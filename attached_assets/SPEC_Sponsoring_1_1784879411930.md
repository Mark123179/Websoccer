# SPEC: Sponsoring-Modul — Blueprint · Online-Fußballmanager

Referenz-Design: `Sponsoring v2.dc.html` (Slot-Board, verbindliche UI-Vorlage) + `Sponsoring.dc.html` Variante 1b (Verhandlungstisch, optionaler Fokus-Modus).
Diese Spec ergänzt `SPEC_Finanzsystem.md` Kap. 6 und ist ohne die zugrundeliegende Diskussion implementierbar. Alle UI-Texte deutsch. Ziel-Shell 1440×900.

---

## 1. Überblick & Grundregeln

- Jeder Verein hat **5 Sponsorenslots**: Hauptsponsor · Trikotsponsor · Ausrüster · Stadionpartner · TV- & Medienpartner.
- Verträge laufen **genau eine Saison**. Zu jedem Saisonstart wird pro Slot ein neuer Satz von **3–4 Angeboten** generiert.
- Alle Angebote sind auf die **Präsidenten-Erwartung** kalibriert (erwartete Siege, Platzierung, Zuschauer der kommenden Saison): gleicher Erwartungswert ± Streuung. Es gibt kein objektiv bestes Angebot, nur Risikoprofile.
- **Nachverhandeln** erhöht den Fixbetrag (und Boni) mit steigendem Abbruchrisiko. Verprellte Sponsoren kehren in dieser Saison nicht zurück.
- **Kein Verein startet ohne Sponsor:** Bleibt in einem Slot nur ein Angebot übrig, gilt es als automatisch angenommen. Ist zum Anpfiff von Spieltag 1 ein Slot noch offen, greift die Auto-Wahl (Kap. 5.4).
- Verhandlungsphase = Saisonvorbereitung (Spieltag 0). Ab „Saison läuft" ist das Modul read-only.

## 3. Sponsorenpool (Stammdaten)

### 3.1 Assets & Import

500 Sponsoren liegen als JPG bereit (Struktur der `sponsors.csv`):

```
/var/www/assets/sponsors/{bereich}/{name}_sponsor.jpg
bereiche: hauptsponsor · trikotsponsor · ausruester · stadionpartner · tv_medien
```

Auslieferung wie alle Assets über Nginx (`ASSETS_BASE_URL=/assets/`). Kein Logo.dev im Produktivcode — die Logo.dev-URLs im Design-Prototyp sind ausschließlich durch lokale Pfade zu ersetzen.

Management-Command `import_sponsors` liest `sponsors.csv` (Format `bereich,name,domain`) und legt `Sponsor`-Objekte an. Anzeigename = Titelform des Slugs mit Sonderfällen-Mapping (z. B. `fritz_kola` → „fritz-kola", `check24` → „CHECK24"); Mapping-Datei `sponsor_names.json` mit ~40 Einträgen, Rest automatisch.

### 3.2 Datenmodell

```python
class Sponsor(models.Model):
    slug        = models.SlugField(max_length=64, unique=True)   # "deutsche_telekom"
    name        = models.CharField(max_length=80)                # "Deutsche Telekom"
    bereich     = models.CharField(max_length=20, choices=BEREICHE)  # = Slot-Typ
    branche     = models.CharField(max_length=40)                # "Telekommunikation" (Anzeige)
    aktiv       = models.BooleanField(default=True)

    @property
    def logo_url(self):
        return f"{settings.ASSETS_BASE_URL}sponsors/{self.bereich}/{self.slug}_sponsor.jpg"

class SponsorOffer(models.Model):
    saison      = models.ForeignKey("game.Season", on_delete=models.CASCADE)
    club        = models.ForeignKey("game.Club", on_delete=models.CASCADE)
    slot        = models.CharField(max_length=20, choices=BEREICHE)
    sponsor     = models.ForeignKey(Sponsor, on_delete=models.PROTECT)
    typ         = models.CharField(max_length=12)   # sicherheit|sieggeld|torgeld|zieljaeger|zuschauer
    fix_start   = models.BigIntegerField()          # generierter Ausgangs-Fixbetrag
    fix_aktuell = models.BigIntegerField()          # nach Nachverhandlungen
    var_rate    = models.BigIntegerField(default=0) # € je Event (bzw. Einmalbonus bei zieljaeger)
    var_ziel    = models.CharField(max_length=32, blank=True)  # z. B. "top6", "klassenerhalt", "titel"
    mult        = models.DecimalField(max_digits=6, decimal_places=4, default=1)  # Boni-Multiplikator
    runde       = models.PositiveSmallIntegerField(default=0)   # 0–3
    status      = models.CharField(max_length=10, default="offen")  # offen|fixiert|abgesagt|verprellt
    class Meta:
        unique_together = ("saison", "club", "slot", "sponsor")

class SponsorContract(models.Model):
    saison      = models.ForeignKey("game.Season", on_delete=models.CASCADE)
    club        = models.ForeignKey("game.Club", on_delete=models.CASCADE)
    slot        = models.CharField(max_length=20, choices=BEREICHE)
    sponsor     = models.ForeignKey(Sponsor, on_delete=models.PROTECT)
    offer       = models.OneToOneField(SponsorOffer, on_delete=models.PROTECT)
    fix_saison  = models.BigIntegerField()
    auto        = models.BooleanField(default=False)  # per Auto-Annahme/Auto-Wahl zustande gekommen
    class Meta:
        unique_together = ("saison", "club", "slot")
```

Kein eigener Zustand außerhalb dieser Tabellen — UI liest ausschließlich Offer/Contract.

## 4. Angebotsgenerierung (Saisonwechsel)

Celery-Job `generate_sponsor_offers` (Teil der Saisonwechsel-Kette, nach Berechnung des Ligakoeffizienten und der Präsidenten-Erwartung):

```
Sponsorwert  = SPONSOR_SOCKEL(Liga) + SPONSOR_MW_ANTEIL × KaderMW + Platzbonus(Vorsaison)   # Finanzspec 6.1
Slotwert(s)  = Sponsorwert × SPONSOR_SLOT_WEIGHTS[s]
```

Je Slot `SPONSOR_OFFERS_PER_SLOT[s]` Angebote:

1. **Kandidaten ziehen:** Sponsoren mit `bereich = slot`, `aktiv = True`, nicht durch Exklusivität (5.6) blockiert. Zufällige Auswahl ohne Wiederholung aus dem gesamten Bereichs-Pool — es gibt keine Größenklassen; die Vereinsgröße wirkt ausschließlich über die Bepreisung (Sponsorwert).
2. **Typen mischen:** Pro Slot genau 1× `sicherheit`; Rest zufällig aus {sieggeld, torgeld, zieljaeger, zuschauer} ohne Doppelung innerhalb des Slots. `torgeld` nie im Slot TV/Medien (thematisch), `zuschauer` immer erlaubt.
3. **Bepreisen** — Erwartungswert jedes Angebots = `Slotwert × (1 ± SPONSOR_STREUUNG × U(0,1))`:

| Typ | Fixanteil | Variabler Teil (auf Präsidenten-Erwartung kalibriert) |
|---|---|---|
| sicherheit | 100 % | — |
| sieggeld | ~50 % | var_rate = Restwert / erwartete Pflichtspielsiege |
| torgeld | ~50 % | var_rate = Restwert / erwartete Pflichtspieltore |
| zieljaeger | ~60 % | Einmalbonus = Restwert / P(Ziel); **Ziel = Saisonziel aus der Präsidenten-Erwartung** (z. B. „Top 6", „Klassenerhalt", Liga 2: „Aufstieg") — keine eigene Schwellen-Tabelle, `var_ziel` übernimmt exakt das Präsidenten-Ziel |
| zuschauer | ~50 % | var_rate = Restwert / erwartete Saison-Stadionbesucher (aus Nachfragemodell Kap. 5 Finanzspec) |

Rundung: Fixbeträge auf 10.000 €, var_rate auf sinnvolle Stellen (≥1 Mio → 10.000er, ≥1.000 → 1.000er, sonst 2 Dezimalstellen bei €/Besucher).

4. Alte Offers der Vorsaison bleiben historisch bestehen (Status unverändert), Contracts der Vorsaison laufen aus.

## 5. Verhandlungsmechanik

### 5.1 Annehmen
`POST /sponsoring/accept` (offer_id). Nur wenn: Phase = Vorbereitung, Slot ohne Contract, Offer `offen`. Erzeugt `SponsorContract` (fix_saison = fix_aktuell), setzt alle anderen Offers des Slots auf `abgesagt`. Meldung: „{Slot} fixiert: {Sponsor} — {fix} € Fixbetrag pro Saison."

### 5.2 Nachverhandeln
`POST /sponsoring/push` (offer_id). Nur wenn: Phase = Vorbereitung, Slot offen, Offer `offen`, `runde < 3`, **mindestens 2 aktive Offers im Slot** (das letzte verbliebene Angebot ist nie verhandelbar — Auto-Annahme-Schutz, Button zeigt „Verhandlung gesperrt").

Ablauf serverseitig (eine Transaktion):
```
risiko = min(95, SPONSOR_PUSH_RISKS[runde] × riskmult(SPONSOR_RISK_MODE))
if random() < risiko:
    offer.status = "verprellt"          # kehrt diese Saison nicht zurück
else:
    gain = SPONSOR_PUSH_GAINS[runde]
    offer.fix_aktuell = round10k(fix_aktuell × (1 + gain/100))
    offer.mult       *= (1 + gain/100)   # Boni steigen mit
    offer.runde      += 1
```
Response liefert das Ergebnis; das Frontend spielt Pending-Puls (1 s), Erfolgs-/Fehlschlag-Flash und Count-up wie im Design. **Der Zufallswurf passiert ausschließlich serverseitig.**

### 5.3 Auto-Annahme (letztes Angebot)
Wird durch Verprellen die Zahl aktiver Offers eines Slots 1, erhält dieses Offer das Badge „Auto-Annahme zum Saisonstart". Der Manager kann es weiterhin sofort fixieren („Jetzt fixieren"), aber nicht mehr nachverhandeln.

### 5.4 Auto-Wahl zum Anpfiff
Celery-Job `finalize_sponsor_contracts` unmittelbar vor Spieltag 1. Für jeden Slot ohne Contract:
- genau 1 aktives Offer → Contract zu dessen `fix_aktuell` (auto=True).
- mehrere aktive Offers → das `sicherheit`-Offer, sonst das mit höchstem Fix; Contract zum **Ausgangswert `fix_start`** (Verhandlungsgewinne verfallen — wer nicht abschließt, verschenkt sie; entspricht Design-Verhalten `autoBase`). auto=True.
- Meldung in Vereinsnews: „{Slot} per Auto-Wahl besetzt: {Sponsor}, {fix} € fix."

KI-Vereine (ohne Manager) überspringen die Verhandlung komplett: `finalize` fixiert für sie zum Saisonstart je Slot ein zufälliges Offer zum Startwert (leichte Präferenz sicherheit 40 %).

### 5.5 Phasen-Sperre
Ab „Saison läuft" sind accept/push serverseitig abgelehnt (403 + Meldung), UI rendert read-only mit fixierten Verträgen.

### 5.6 Exklusivität
`SPONSOR_EXCLUSIVITY = "liga"`: Ein Sponsor kann pro Saison und Liga nur **einen** Contract halten. Bei der Angebotsgenerierung werden Sponsoren, die bereits einen Contract in der Liga haben, nicht gezogen; Offers verschiedener Vereine auf denselben Sponsor sind erlaubt (wer zuerst fixiert, gewinnt — die Offers der anderen werden auf `abgesagt` gesetzt mit Ticker-Meldung „{Sponsor} hat sich für {Verein} entschieden.").

## 6. Buchungen (Ledger)

Neue Buchungstypen: `SPONSOR_FIX`, `SPONSOR_BONUS`. Beide Quellen (Schöpfung) im Sinne von Finanzspec Kap. 3.

- **Fix:** je Ligaspieltag `fix_saison / Ligaspieltage` (Rundungsrest im letzten Spieltag), gebucht im bestehenden Spieltags-Abrechnungsjob.
- **sieggeld:** `var_rate × mult` je Pflichtspielsieg, gebucht mit der Spielabrechnung.
- **torgeld:** `var_rate × mult` je eigenem Pflichtspieltor, ebenso.
- **zuschauer:** `var_rate × mult × Heimzuschauer` je Heimpflichtspiel, mit der Spieltagsabrechnung.
- **zieljaeger:** Einmalbuchung im Saisonabschluss-Job, wenn `var_ziel` erreicht.

Alle Buchungen mit Referenz auf `SponsorContract` (Ledger bleibt einzige Wahrheit, Finanzspec 12.1).

## 7. UI (verbindlich: Design v2)

Route `/finanzen/sponsoring/`, Template im bestehenden 1440×900-Shell, CSS-Tokens aus dem MatchEngine-Design-System (`_ds/`-Bundle liegt dem Design-Export bei — Farben/Typo von dort übernehmen, nicht neu erfinden).

Umzusetzende Elemente aus `Sponsoring v2.dc.html`:
1. **KPI-Leiste:** Sponsorwert (Schätzung) · Erwartetes Volumen · Slots fixiert (n/5) · Verprellte Sponsoren · Regeltext.
2. **5 Slot-Karten** (aufklappbar, eine offen): Statuspunkt (offen cyan / auto gelb / fixiert grün), Slotwert bzw. Vertragswert, bei fixiert Mini-Logo + Sponsorname.
3. **Angebotskarten** je Slot: Logo (weißer Kachel-Hintergrund, `center/76% no-repeat`), Name, Branche, Typ-Badge (Farben: sicherheit cyan · sieggeld/torgeld grün · zieljaeger gelb · zuschauer orange), Fixbetrag, Variabler-Teil-Zeile, „≈ erwartet · max"-Zeile, Delta-Zeile nach Verhandlung (Start → +X fix · Boni +Y %), Abbruchrisiko-Balken mit Prozent (grün <25, gelb <50, rot sonst), Runden-Punkte (0–3), Buttons **Annehmen** / **Nachverhandeln +X %** mit allen Disabled-Zuständen aus dem Design (verprellt/abgesagt gedimmt 0.42, pending-Puls, Flash ok/fail, Count-up 600 ms).
4. **Szenario-Projektion** (Panel rechts): Worst (nur Fix) / Erwartet / Best (alle Boni) + Balken Fix/Variabel/Offen-Anteil. Offene Slots zählen mit Slotwert-Schätzung.
5. **Präsidenten-Erwartung** (Panel): Platzierung, Pflichtspielsiege, Zuschauer/Saison — Werte aus derselben Quelle wie die Bepreisung.
6. **Liga-Ticker:** echte Fixierungen anderer Vereine derselben Liga (aus Contract-Erzeugung gespeist, neueste zuerst, Poll alle 30 s oder in bestehende Vereinsnews-Infrastruktur integriert). Kein Fake-Content.
7. **Meldungsbanner** oben (6 s auto-hide) für alle Aktionen.

Nicht umsetzen: „Zurücksetzen"-Button (nur Prototyp-Feature) — stattdessen Admin-Reset in der KI-Transferzentrale (Kap. 8).

Variante 1b (Verhandlungstisch) ist **nicht** Teil des MVP; Layout-Entscheidung fiel auf das Slot-Board.

## 8. Admin (Creator Mode / KI-Transferzentrale)

- Regler: SPONSOR_RISK_MODE (Entschärft/Standard/Hardcore), Push-Gains/-Risks, Slot-Weights — live über EconomyParameter.
- Aktionen je Verein: Offers neu generieren (Dry-Run-Vorschau wie beim Transfersystem), Slot-Reset (Contracts + Offers der Saison löschen und neu würfeln), Sponsor deaktivieren (aktiv=False, greift ab nächster Generierung).
- Monitoring: Summe SPONSOR_FIX/BONUS pro Saison im Datencenter-Ledger-Dashboard (Finanzspec 12.5).
