# Implementierungsauftrag: Lokaler Vereins- und Spielerimporter für den Creator-Mode

## 1. Projektkontext

Dieses Projekt ist ein browserbasierter Fußballmanager auf Basis von:

* Django
* PostgreSQL/Supabase
* Replit
* bestehendem Creator-Mode für administrative Funktionen
* bestehendem Spieler-, Vereins- und Spielstärkensystem
* bestehender Berechnungslogik für FMInside- und SoFIFA-Werte

Es soll ein neuer Importprozess entstehen, mit dem ein Administrator im Creator-Mode einen Transfermarkt-Verein anhand seiner Transfermarkt-Vereins-ID importieren beziehungsweise aktualisieren kann.

Der eigentliche Abruf der Webseiten soll **nicht auf dem Replit-Server** erfolgen.

Stattdessen wird ein lokaler Importer auf einem Windows-PC ausgeführt. Dieser öffnet sichtbar Microsoft Edge, liest die gerenderten Webseiten aus und übermittelt die Ergebnisse über eine geschützte API an den Creator-Mode.

Es wird keine CSV als notwendiger Zwischenschritt verwendet.

Der vollständige Ablauf lautet:

```text
Creator-Mode:
Importauftrag anlegen
    ↓
Lokaler Windows-Importer:
offenen Auftrag abrufen
    ↓
Microsoft Edge:
Transfermarkt, FMInside und SoFIFA öffnen
    ↓
Lokaler Importer:
Rohdaten strukturiert erfassen
    ↓
Geschützte Django-API:
Ergebnisse übertragen
    ↓
Creator-Mode:
Importvorschau und Kontrolle
    ↓
Administrator:
Spieler auswählen und vorhandene Spieler optional überschreiben
    ↓
Django:
Daten direkt in die bestehende Datenbank übernehmen
```

---

# 2. Wichtige Grundregeln

## 2.1 Keine CSV im regulären Prozess

Es soll keine CSV heruntergeladen und anschließend wieder hochgeladen werden müssen.

Die Daten werden als JSON vom lokalen Importer an Django übertragen und dort zunächst als temporärer Importauftrag gespeichert.

Eine CSV-Importfunktion ist für diese Funktion nicht erforderlich.

## 2.2 Keine serverseitige Browsersteuerung

Playwright beziehungsweise Microsoft Edge laufen ausschließlich auf dem lokalen Windows-PC.

Der Replit-Server:

* öffnet keine Transfermarkt-Seiten,
* startet keinen Browser,
* führt kein serverseitiges Webscraping durch.

## 2.3 Microsoft Edge

Der lokale Importer soll den installierten Microsoft Edge verwenden:

```python
channel="msedge"
```

Der Browser soll sichtbar geöffnet werden:

```python
headless=False
```

Es soll ein eigenes permanentes Browserprofil für den Importer verwendet werden, beispielsweise:

```text
edge_import_profile/
```

Dadurch bleiben Cookies und lokale Einstellungen erhalten. Das normale persönliche Edge-Profil des Benutzers darf nicht direkt verwendet werden.

## 2.4 Nur Rohdaten importieren

Der lokale Importer soll keine Spielstärke und keine endgültigen kombinierten Attribute berechnen.

FMInside- und SoFIFA-Daten müssen getrennt als Rohwerte gespeichert werden.

Die bereits bestehende interne Berechnungslogik des Managers übernimmt danach beispielsweise:

* Basisstärke
* Potential
* kombinierte Attribute
* Fallback bei fehlendem SoFIFA
* Positionsfit
* sonstige interne Berechnungen

Bestehende Berechnungsdienste dürfen nicht dupliziert oder ersetzt werden.

## 2.5 Spielerbilder

Spielerbilder sind ausdrücklich nicht Bestandteil dieses Imports.

Keine Bilddateien und keine Bild-URLs importieren.

# 3. Vor Beginn der Implementierung

Untersuche zuerst die bestehende Codebasis vollständig.

Insbesondere prüfen:

1. Welches Django-Modell aktuell Spieler repräsentiert.
2. Welches Modell Vereine repräsentiert.
3. Welche Felder bereits für Transfermarkt, FMInside und SoFIFA existieren.
4. Wo die Berechnung von Stärke, Potential und Attributen stattfindet.
5. Wie der Creator-Mode aufgebaut ist.
6. Welche Berechtigungsprüfung für Creator-/Admin-Funktionen verwendet wird.
7. Ob Django REST Framework verwendet wird.
8. Ob bereits Importskripte, Parser oder Matchingfunktionen existieren.
9. Welche Felder einem importierten Spieler gehören und welche Daten in separaten Saison-, Statistik- oder Matchmodellen liegen.
10. Wie Spieler aktuell einem WS-Verein zugeordnet sind.

Keine parallelen zweiten Spieler- oder Vereinsmodelle erstellen.

Bestehende Modelle und Dienste erweitern.

Falls das Projekt kein Django REST Framework verwendet, soll für diese einzelne Funktion nicht unnötig DRF eingeführt werden. Dann normale Django-JSON-Views verwenden.

Vor dem Umbau eine kurze technische Bestandsaufnahme ausgeben:

* betroffene Modelle,
* betroffene Views,
* bestehende Berechnungsdienste,
* geplante neue Dateien,
* notwendige Migrationen,
* erkennbare Risiken.

Danach die Implementierung durchführen.

# 4. Creator-Mode: Importauftrag erstellen

Im Creator-Mode wird eine neue Importzentrale benötigt.

Beispielbezeichnung:

```text
Vereins- und Spielerimport
```

Der Administrator soll dort Folgendes auswählen beziehungsweise eingeben:

```text
WS-Verein:              [bestehenden Verein auswählen]
Transfermarkt-Vereins-ID: [41]

[Importauftrag erstellen]
```

Nicht benötigt werden:

* Land
* Liga
* Saison als manuelle Eingabe
* Spielerbilder
* CSV-Datei

Der WS-Verein wird manuell aus den bereits existierenden Vereinen der Datenbank ausgewählt.

Beispiel:

```text
WS-Verein: Hamburger SV
TM-Vereins-ID: 41
```

Der ausgewählte Verein wird später bei allen gefundenen Spielern als `ws_club` gesetzt.

# 5. Automatische Saisonlogik

Die Transfermarkt-Saison-ID wird automatisch anhand des aktuellen Datums berechnet.

Zeitzone:

```text
Europe/Berlin
```

Regel:

```text
01.01. bis 30.06. eines Jahres:
Saison-ID = aktuelles Jahr - 1

Ab 01.07. eines Jahres:
Saison-ID = aktuelles Jahr
```

Beispiele:

```text
16.06.2026 → Saison-ID 2025 → Saison 2025/26
30.06.2026 → Saison-ID 2025 → Saison 2025/26
01.07.2026 → Saison-ID 2026 → Saison 2026/27
15.08.2026 → Saison-ID 2026 → Saison 2026/27
```

Implementiere hierfür eine zentrale Funktion, zum Beispiel:

```python
def get_current_tm_season_id(reference_date=None) -> int:
    ...
```

Die berechnete Saison-ID muss im Importauftrag gespeichert und im Creator-Mode angezeigt werden.

Beispiel:

```text
Transfermarkt-Saison-ID: 2025
Saison: 2025/26
```

Die Saison darf während eines bereits gestarteten Importauftrags nicht nachträglich neu berechnet werden. Der Auftrag behält seine bei der Erstellung ermittelte Saison-ID.

```python
    created_by = models.ForeignKey(...)
```

# 7. Temporäre Spielerkandidaten

Für jeden gefundenen Spieler wird zunächst ein temporärer Importkandidat gespeichert.

Beispielstruktur:

```python
class PlayerImportCandidate(models.Model):
    job = models.ForeignKey(
        ClubPlayerImportJob,
        related_name="candidates",
        on_delete=models.CASCADE,
    )

    tm_player_id = models.PositiveBigIntegerField()
    existing_player = models.ForeignKey(
        Player,
        null=True,
        blank=True,
        on_delete=models.SET_NULL,
    )

    status = models.CharField(...)
    selected_for_import = models.BooleanField(default=False)
    overwrite_existing = models.BooleanField(default=False)

    tm_raw = models.JSONField(default=dict)
    position_raw = models.JSONField(default=dict)
    fmi_raw = models.JSONField(default=dict)
    sofifa_raw = models.JSONField(default=dict)

    normalized_data = models.JSONField(default=dict)
    detected_changes = models.JSONField(default=dict)
    validation_errors = models.JSONField(default=list)
    source_warnings = models.JSONField(default=list)

    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)
```

Eindeutige Bedingung:

```text
Ein TM-Spieler darf innerhalb eines Importauftrags nur einmal vorkommen.
```

Daher eine UniqueConstraint für:

```text
job + tm_player_id
```

Mögliche Kandidatenstatus:

```text
new
existing_changed
existing_unchanged
missing_fmi
missing_sofifa
ambiguous_fmi
ambiguous_sofifa
invalid
source_error
ready
imported
skipped
```

SoFIFA darf fehlen.

FMInside gilt grundsätzlich als erwartete Quelle. Fehlt FMInside, muss der Spieler in der Kontrollansicht deutlich als unvollständig beziehungsweise prüfbedürftig angezeigt werden.

# 8. Transfermarkt: Kaderseite

Ausgangspunkt ist:

* Transfermarkt-Vereins-ID
* automatisch bestimmte Saison-ID

Beispiel:

```text
HSV:
TM-Vereins-ID 41
TM-Saison-ID 2025
```

Der Importer soll die kanonische Transfermarkt-Kaderseite anhand dieser Werte öffnen.

Der Vereinsname beziehungsweise URL-Slug darf nicht fest im Code hinterlegt werden.

Die Implementierung muss mit beliebigen Transfermarkt-Vereins-IDs funktionieren.

Falls Transfermarkt einen Slug benötigt, soll der Importer:

1. die Seite über Vereins-ID beziehungsweise Such-/Weiterleitungslogik aufrufen,
2. die kanonische URL nach der Weiterleitung verwenden,
3. nicht auf einen bestimmten Vereinsnamen angewiesen sein.

Von der aktuellen Kaderseite werden **alle dort aufgeführten Spieler** übernommen.

Es werden nicht zusätzlich frühere Kader, Abgänge oder Jugendseiten durchsucht.

Doppelte Spielerlinks müssen anhand der TM-Spieler-ID entfernt werden.

# 9. Transfermarkt: Spieler-Stammdaten

Für jeden Spieler werden vom Spielerprofil folgende Werte erfasst:

* Transfermarkt-Spieler-ID
* kanonischer Transfermarkt-Profillink
* vollständiger Anzeigename
* Vorname
* Nachname
* Geburtsdatum
* Größe
* bevorzugter Fuß
* Staatsbürgerschaft beziehungsweise Nationalitäten
* aktuelle Marktwertangabe
* Profilposition als Fallback
* reale Vereins- und Leihsituation

Beispielprofil:

```text
https://www.transfermarkt.de/luka-vuskovic/profil/spieler/892160
```

Beispiel-ID:

```text
892160
```

## 9.1 Datentypen

Geburtsdatum:

```text
ISO-Format YYYY-MM-DD
```

Alter nicht fest importieren.

Das Alter wird im Manager aus dem Geburtsdatum berechnet.

Größe:

```text
1,93 m → 193
```

Als Zentimeter-Integer speichern.

Marktwert:

```text
35,00 Mio. € → 35000000
500 Tsd. € → 500000
```

Als ganzzahligen Eurobetrag speichern.

Keine formatierten Texte wie `35 Mio.` in der Datenbank verwenden.

Fuß auf die im Projekt bestehenden Werte normalisieren, beispielsweise:

```text
links
rechts
beidfüßig
```

## 9.2 Nationalitäten

Alle auf Transfermarkt genannten Nationalitäten erfassen.

Die erste Nationalität gilt als Hauptnationalität.

Beispiel:

```json
{
  "primary_nationality": "Kroatien",
  "nationalities": ["Kroatien"]
}
```

Bei mehreren Nationalitäten:

```json
{
  "primary_nationality": "Deutschland",
  "nationalities": ["Deutschland", "Türkei"]
}
```

Bestehende Länder-/Nationalitätenmodelle wiederverwenden, falls vorhanden.

Keine neuen Länder-Dubletten aufgrund unterschiedlicher Schreibweisen erzeugen.

# 10. Vereins- und Leihlogik

Es werden genau diese drei Zuordnungen benötigt:

```text
WS Club
Real Club
Loaned From
```

## 10.1 WS Club

`ws_club` ist immer der Verein, den der Administrator bei der Erstellung des Importauftrags ausgewählt hat.

Beispiel:

```text
Importauftrag:
WS-Verein = Hamburger SV

Alle Spieler des Imports:
ws_club = Hamburger SV
```

## 10.2 Normaler Spieler ohne Leihe

Beispiel:

```text
WS Club: Hamburger SV
Real Club: Hamburger SV
Loaned From: leer
```

## 10.3 Leihspieler

Wenn ein Spieler auf der Kaderseite eines Vereins steht und als ausgeliehen gekennzeichnet ist, muss der Stammverein über die Leihkennzeichnung beziehungsweise den verlinkten Verein erkannt werden.

Beispiel Luka Vušković im HSV-Import:

```text
WS Club: Hamburger SV
Real Club: Tottenham Hotspur
Loaned From: Tottenham Hotspur
```

Der importierende WS-Verein bleibt der HSV.

Der reale Stammverein und `loaned_from` werden auf Tottenham gesetzt.

## 10.4 Fehlender Real Club in der Datenbank

Falls der reale Stammverein beziehungsweise `loaned_from` noch nicht in der Datenbank existiert, wird automatisch ein minimaler Platzhalterverein erstellt.

Beispiel:

```text
Name: Tottenham Hotspur
TM-Vereins-ID: erkannte TM-ID
TM-Link: kanonischer Vereinslink
Platzhalter: Ja
```

Nicht automatisch ergänzen:

* Liga
* Land, sofern nicht zwingend technisch nötig
* Stadion
* Wappen
* Finanzen
* Manager
* Kader
* Wettbewerbe

Vorhandene Vereine vorrangig über die TM-Vereins-ID erkennen.

Fallback nur bei fehlender TM-ID:

```text
normalisierter exakter Vereinsname
```

Keine Vereinsdubletten erzeugen.

# 13. Algorithmus für HP und NP

Die Positionen werden zunächst nach der Zahl der absolvierten Spiele absteigend sortiert.

## 13.1 Reguläre Hauptpositionen

* maximal zwei reguläre Hauptpositionen
* eine Hauptposition benötigt grundsätzlich mindestens 25 Einsätze

Beispiel:

```text
IV 90 → HP
DM 42 → HP
```

## 13.2 Nebenpositionen

* maximal zwei Nebenpositionen
* eine Nebenposition benötigt mindestens 10 Einsätze
* Positionen unter 10 Einsätzen werden ignoriert

Beispiel:

```text
IV 90 → HP
DM 42 → HP
ZM 22 → NP
RV 14 → NP
ST 7  → ignorieren
```

## 13.3 Immer mindestens eine HP

Jeder Spieler muss mindestens eine Hauptposition erhalten.

Beispiel:

```text
IV 22
DM 15
```

Ergebnis:

```text
HP: IV
NP: DM
```

Die meistgespielte Position wird zur HP, obwohl sie die reguläre Schwelle von 25 Spielen nicht erreicht.

## 13.4 Jugendspieler ohne Positionseinsätze

Wenn überhaupt keine auswertbaren Positionseinsätze vorhanden sind:

1. die im Transfermarkt-Spielerprofil genannte Position verwenden,
2. diese Position über das Mapping umwandeln,
3. diese Position als HP setzen.

Beispiel:

```text
Profilposition: Innenverteidiger
Keine Leistungsdaten vorhanden

Ergebnis:
HP: IV
```

Wenn auch die Profilposition nicht gemappt werden kann, ist der Spieler nicht importbereit und erhält einen Validierungsfehler.

## 13.5 Mehr als zwei Positionen mit mindestens 25 Einsätzen

Es bleiben maximal zwei reguläre HP.

Weitere Positionen werden in der sortierten Reihenfolge als NP behandelt, sofern noch NP-Plätze frei sind und mindestens 10 Einsätze bestehen.

Beispiel:

```text
IV 100
DM 80
ZM 60
RV 30
```

Ergebnis:

```text
HP: IV, DM
NP: ZM, RV
```

# 14. Automatisch abgeleitete zusätzliche HP

Bestimmte Kombinationen zweier Hauptpositionen erzeugen eine zusätzliche dritte Hauptposition.

Regeln:

```text
HP LV + HP LM → zusätzliche HP LOV
HP RV + HP RM → zusätzliche HP ROV
HP LM + HP LF → zusätzliche HP LOM
HP RM + HP RF → zusätzliche HP ROM
```

Diese zusätzliche Position:

* ist eine echte HP,
* verbraucht keinen NP-Platz,
* entsteht nur, wenn beide Ausgangspositionen HP sind,
* entsteht nicht, wenn eine der Ausgangspositionen nur NP ist.

Beispiele:

```text
HP: LV, LM
Ergebnis: LV, LM, LOV
```

```text
HP: LM, LF
Ergebnis: LM, LF, LOM
```

```text
HP: LV
NP: LM
Ergebnis: keine automatische LOV-Position
```

Die Funktion zur Positionsberechnung muss als eigenständige, vollständig testbare Servicefunktion implementiert werden.

# 15. FMInside-Matching

Nachdem Transfermarkt-Daten vorhanden sind, wird der Spieler auf FMInside gesucht.

FMInside gilt als erwartete Hauptquelle für die zusätzlichen Rohdaten.

Matching-Reihenfolge:

1. normalisierter Name,
2. exaktes Geburtsdatum,
3. Nationalität als zusätzliche Absicherung,
4. Verein als zusätzlicher Tie-Breaker.

Das Geburtsdatum ist das wichtigste Identitätsmerkmal neben dem Namen.

Normalisierung muss unter anderem berücksichtigen:

* Groß-/Kleinschreibung
* überflüssige Leerzeichen
* Bindestriche
* Apostrophe
* Akzente und diakritische Zeichen
* unterschiedliche Unicode-Darstellungen

Ein Spieler darf nicht automatisch allein anhand eines ähnlichen Namens zugeordnet werden.

## 15.1 Eindeutiger Treffer

Bei eindeutigem Namen und identischem Geburtsdatum:

```text
automatisch übernehmen
```

## 15.2 Mehrere mögliche Treffer

Wenn mehrere plausible FMInside-Spieler vorhanden sind:

```text
Status: ambiguous_fmi
```

Die möglichen Treffer müssen im Creator-Mode angezeigt werden.

Der Administrator kann dort den richtigen Treffer auswählen.

## 15.3 Kein Treffer

Wenn kein passender FMInside-Spieler gefunden wird:

```text
Status: missing_fmi
```

Der übrige Importauftrag läuft weiter.

Der Spieler wird nicht verworfen, sondern zur manuellen Kontrolle angezeigt.

# 18. SoFIFA-Matching

Nach FMInside wird SoFIFA durchsucht.

Matching ebenfalls über:

1. normalisierten Namen,
2. exaktes Geburtsdatum,
3. Nationalität,
4. Verein als Tie-Breaker.

## 18.1 SoFIFA ist optional

Es kann vorkommen, dass insbesondere junge Spieler noch nicht bei SoFIFA vorhanden sind.

Ein fehlender SoFIFA-Spieler darf den Import nicht blockieren.

Mögliche Zustände:

```text
TM + FMI + SoFIFA → vollständig
TM + FMI          → importierbar, SoFIFA fehlt
TM ohne FMI       → manuelle Prüfung erforderlich
```

## 18.2 Mehrere Treffer

Bei mehreren Treffern:

```text
Status: ambiguous_sofifa
```

Die Treffer müssen in der Kontrollansicht auswählbar sein.

```text
sofifa_heading
sofifa_standing_tackle
sofifa_defensive_awareness
sofifa_vision
sofifa_free_kick_accuracy
sofifa_penalties
```

Der Importer berechnet ausdrücklich nicht:

```text
(Short Passing + Long Passing) / 2
```

Diese Berechnung bleibt im bestehenden internen Rechner.

# 20. SoFIFA-Rohdaten für Torhüter

Für Torhüter werden gespeichert:

* SoFIFA-ID
* SoFIFA-Link
* Rating
* Potential
* Reflexe
* Fangsicherheit
* Stellungsspiel
* Passen

Nutze für „Passen“ das SoFIFA-Torhüterattribut, das bereits im bestehenden Spielstärkesystem beziehungsweise bisherigen Import verwendet wird.

Keine neue Interpretation erfinden, falls im bestehenden Projekt bereits ein Mapping vorhanden ist.

Empfohlene Rohfeldnamen:

```text
sofifa_rating
sofifa_potential
sofifa_gk_reflexes
sofifa_gk_handling
sofifa_gk_positioning
sofifa_gk_passing
```

SoFIFA besitzt in diesem Modell keinen eigenen Wert für `1-gegen-1`.

Dieser Wert stammt ausschließlich von FMInside.

# 21. Bestehende Spieler erkennen

Ein Spieler muss vor dem Import gegen die Datenbank geprüft werden.

Reihenfolge:

1. Transfermarkt-Spieler-ID
2. FMInside-ID
3. SoFIFA-ID
4. normalisierter Name plus identisches Geburtsdatum als Dublettenwarnung

## 21.1 Transfermarkt-ID gefunden

Wenn die TM-Spieler-ID bereits existiert:

```text
Status: bereits vorhanden
```

Zusätzlich Unterschiede zwischen bestehenden und neuen Importdaten berechnen.

## 21.2 Nur Name und Geburtsdatum gefunden

Nicht automatisch überschreiben.

Stattdessen:

```text
Status: mögliche Dublette
```

Im Creator-Mode muss angezeigt werden, welcher bestehende Spieler möglicherweise gemeint ist.

## 21.3 Keine Übereinstimmung

```text
Status: neuer Spieler
```

Neue Spieler sollen in der Kontrollansicht standardmäßig zum Import ausgewählt sein.

Vorhandene Spieler sollen standardmäßig nicht zum Überschreiben ausgewählt sein.

# 25. Bedeutung von „vollständig überschreiben“

Beim Überschreiben sollen keine alten importierten Stammdaten oder Quellenwerte erhalten bleiben.

Alle importverwalteten Spielerfelder werden durch den neuen Importstand ersetzt.

Dazu gehören insbesondere:

* Vorname
* Nachname
* vollständiger Name
* Geburtsdatum
* Größe
* Fuß
* Hauptnationalität
* alle Nationalitäten
* Marktwert
* Profilposition
* HP
* NP
* WS Club
* Real Club
* Loaned From
* TM-ID
* TM-Link
* FMI-ID
* FMI-Link
* alle FMI-Rohwerte
* SoFIFA-ID
* SoFIFA-Link
* alle SoFIFA-Rohwerte
* daraus neu berechnete Stärke- und Potentialwerte

Wichtig:

Wenn ein alter SoFIFA-Wert existiert, der Spieler beim neuen Import aber nicht mehr eindeutig auf SoFIFA gefunden wurde, darf nicht stillschweigend der alte Wert erhalten bleiben.

Der neue Importstand ist maßgeblich.

Entsprechende alte importierte Quellwerte werden auf `NULL` beziehungsweise leer gesetzt.

Der Spieler-Datenbankdatensatz darf jedoch nicht gelöscht und neu erstellt werden, wenn dadurch Beziehungen zerstört würden.

Nicht löschen:

* technische Primary Keys
* bestehende Match-Events
* historische Saisonstatistiken in separaten Tabellen
* Transferhistorien in separaten Tabellen
* sonstige Foreign-Key-Beziehungen

Das Überschreiben erfolgt als vollständiges Update aller importverwalteten Felder auf dem bestehenden Spielerobjekt.

Anschließend den bestehenden internen Berechnungsdienst ausführen.

# 26. Datenbankimport

Der endgültige Import muss serverseitig erfolgen.

Für jeden ausgewählten Spieler:

1. Kandidat erneut validieren.
2. Bestehenden Spieler erneut anhand der IDs prüfen.
3. Platzhaltervereine bei Bedarf erstellen.
4. Spieler innerhalb einer Datenbanktransaktion erstellen oder aktualisieren.
5. Nationalitäten aktualisieren.
6. HP und NP vollständig ersetzen.
7. FMI-Rohwerte vollständig ersetzen.
8. SoFIFA-Rohwerte vollständig ersetzen.
9. interne Berechnung der Stärke und Attribute ausführen.
10. Import-Audit speichern.
11. Kandidatenstatus auf `imported` setzen.

Verwende mindestens eine `transaction.atomic()`-Transaktion pro Spieler.

Ein Fehler bei einem einzelnen Spieler darf nicht zwingend den gesamten Vereinsimport zerstören.

Am Ende eine Zusammenfassung liefern:

```text
Erfolgreich erstellt: 5
Erfolgreich aktualisiert: 14
Übersprungen: 7
Fehlgeschlagen: 1
```

Fehler müssen mit genauer Meldung am jeweiligen Kandidaten sichtbar bleiben.

---

# 27. Import-Audit

Jeder verbindliche Import soll nachvollziehbar sein.

Speichere mindestens:

* Importauftrag
* importierender Administrator
* Zeitpunkt
* Spieler
* Aktion `created` oder `updated`
* Daten vor dem Import
* Daten nach dem Import
* erkannte Quellen
* verwendete Saison-ID

Falls bereits ein Audit-/Historien-System existiert, dieses verwenden.

Keine unnötige zweite Historienlösung erstellen.

# 28. Geschützte Importer-API

Der lokale Importer benötigt eine kleine, geschützte API.

Der API-Zugang wird über einen langen geheimen Token abgesichert.

Serverumgebungsvariable:

```text

```

Der Token darf nicht im GitHub-Repository gespeichert werden.

HTTP-Header:

```text
Authorization: Bearer <TOKEN>
```

Alle Aufrufe ausschließlich über HTTPS.

Mögliche Endpunkte:

```text

POST /creator-api/import-jobs/<id>/candidates/
POST /creator-api/import-jobs/<id>/complete/
POST /creator-api/import-jobs/<id>/fail/
```

# 30. Permanente BAT-Datei

Es soll nur eine dauerhafte BAT-Datei geben.

Nicht für jeden Verein eine neue BAT erzeugen.

Bezeichnung:

```text
CFM_Importer_Start.bat
```

Die BAT soll:

1. in ihr eigenes Verzeichnis wechseln,
2. prüfen, ob eine virtuelle Python-Umgebung existiert,
3. diese bei Bedarf erstellen,
4. benötigte Pakete installieren beziehungsweise aktualisieren,
5. den Importer starten,
6. bei Fehlern das Fenster geöffnet lassen.

Beispielgrundstruktur:

```bat
@echo off
setlocal
cd /d "%~dp0"

if not exist ".venv\Scripts\python.exe" (
    py -3 -m venv .venv
)

call ".venv\Scripts\activate.bat"

python -m pip install --upgrade pip
python -m pip install -r requirements.txt

python importer.py

echo.
echo Importer wurde beendet.
pause
```

Die endgültige BAT muss mit deutschen Windows-Pfaden und Leerzeichen in Verzeichnissen umgehen können.

Keine absoluten benutzerspezifischen Pfade einbauen.

# 33. Browser- und Seitenverhalten

Verwende Playwright mit Microsoft Edge und einem persistenten Kontext.

Beispiel:

```python
context = playwright.chromium.launch_persistent_context(
    user_data_dir=edge_profile_path,
```

Regeln:

* keine Stealth-Plugins,
* keine Captcha-Umgehung,
* keine Schutzmechanismen umgehen,
* keine parallelen Dutzenden Browserseiten,
* Seiten grundsätzlich sequenziell verarbeiten,
* angemessene Pausen zwischen Seiten,
* bei HTTP 403 oder 429 stoppen beziehungsweise deutlich warnen,
* bei manueller Abfrage dem Benutzer ermöglichen, im sichtbaren Edge zu reagieren.

Der Importer soll bei einer nicht geladenen Seite nicht sofort falsche Leerwerte speichern.

# 35. Fortsetzen nach Abbruch

Der lokale Importer soll einen unterbrochenen Auftrag fortsetzen können.

Dafür:

* bereits übertragene TM-Spieler-IDs serverseitig abrufen oder lokal speichern,
* bereits vollständig verarbeitete Spieler überspringen,
* einen Auftrag nicht zwingend von vorne beginnen.

Lokale Statusdateien beispielsweise:

```text
state/job_184.json
```

Die Datenbank bleibt die maßgebliche Quelle.

Lokale Dateien dienen nur als zusätzliche Wiederaufnahmehilfe.

# 36. Fortschrittsanzeige im Creator-Mode

# 37. Manuelle Quellenkorrektur

Bei uneindeutigen Treffern soll der Administrator im Creator-Mode mögliche Kandidaten sehen.

Beispiel:

```text
FMInside-Treffer auswählen:

○ Luka Vuskovic, 24.02.2007, Kroatien
○ Luka Vuskovic, 12.08.2005, Serbien
○ Kein Treffer
```

Nach Auswahl:

* gewählten Quellenlink speichern,
* Rohdaten des ausgewählten Profils verwenden,
* Kandidatenvalidierung erneut ausführen.

Falls technisch sinnvoll, kann der lokale Importer bereits mehrere Treffer samt Basisdaten übertragen.

Der Server soll nicht eigenständig externe Seiten abrufen.

# 38. Sicherheitsanforderungen

Die Importfunktion ist ausschließlich für Creator-/Admin-Nutzer.

Erforderlich:

* bestehende Creator-Berechtigungsprüfung
* HTTPS
* Bearer-Token für lokalen Importer
* Token aus Umgebungsvariable
* keine Tokens im Browser-JavaScript
* keine Tokens in Logs
* keine Tokens im Repository
* Größenlimit für API-Payloads
* Validierung aller IDs
* erlaubte Felder serverseitig fest definieren
* Importer darf keine beliebigen Modellfelder bestimmen
* Audit-Log
* Rate-Limit für API-Endpunkte
* sichere Fehlerausgaben ohne Secrets

Bei reinen Token-API-Endpunkten kann CSRF deaktiviert werden, aber nur dort.

Die Creator-Weboberfläche bleibt normal CSRF-geschützt.

# 39. Validierung

Vor dem Import eines Kandidaten mindestens prüfen:

* TM-Spieler-ID vorhanden
* Name vorhanden
* Geburtsdatum gültig
* mindestens eine HP vorhanden
* WS Club vorhanden
* Real Club vorhanden oder erstellbar
* Nationalitätenstruktur gültig
* Marktwert nicht negativ
* Größe in plausiblem Bereich oder leer
* FMI-Werte zwischen den erwarteten Grenzen
* SoFIFA-Werte zwischen den erwarteten Grenzen
* keine doppelte TM-ID innerhalb des Auftrags
* URLs nur von erwarteten Domains

Keine ungültigen Werte stillschweigend auf `0` setzen.

Fehlender Wert soll `NULL` beziehungsweise leer bleiben.

# 43. Fehlerbehandlung

Der Import darf bei einem einzelnen Fehler nicht vollständig abbrechen.

Beispiele:

```text
Transfermarkt-Profil nicht erreichbar
Positionsseite verändert
FMInside nicht gefunden
SoFIFA nicht gefunden
mehrere FMInside-Treffer
ungültiges Geburtsdatum
Real Club konnte nicht erkannt werden
API-Verbindung kurzzeitig unterbrochen
```

Verhalten:

* Fehler am Spieler speichern
* Import mit nächstem Spieler fortsetzen
* bei API-Problemen Wiederholungsversuche mit Backoff
* bei dauerhaftem API-Ausfall lokal zwischenspeichern
* nach Wiederherstellung weiter übertragen
* bei schwerem allgemeinen Fehler Auftrag auf `failed` setzen
* genaue Meldung im Creator-Mode anzeigen

Keine pauschalen Meldungen wie nur:

```text
Import fehlgeschlagen
```

Stattdessen konkrete Meldungen:

```text
Spieler 892160: Positionstabelle auf der Leistungsdatenseite nicht gefunden.
```

# 48. Definition of Done

Die Aufgabe ist erst abgeschlossen, wenn alle folgenden Punkte erfüllt sind:

* Creator kann einen bestehenden WS-Verein auswählen.
* Creator kann eine Transfermarkt-Vereins-ID eingeben.
* Saison-ID wird automatisch korrekt bestimmt.
* Importauftrag wird gespeichert.
* Eine einzige permanente BAT startet den lokalen Importer.
* Der lokale Importer verwendet sichtbaren Microsoft Edge.
* Der lokale Importer ruft offene Aufträge ab.
* Alle Spieler der aktuellen TM-Kaderseite werden erkannt.
* Spieler-Stammdaten werden gelesen.
* Leihspieler werden erkannt.
* Fehlende reale Vereine werden als minimale Platzhalter erstellt.
* Positionen werden über alle Saisons ausgewertet.
* Jeder Spieler erhält mindestens eine HP.
* HP-/NP-Schwellen funktionieren.
* LOV, ROV, LOM und ROM werden korrekt abgeleitet.
* FMInside wird über Name und Geburtsdatum zugeordnet.
* SoFIFA wird über Name und Geburtsdatum zugeordnet.
* Fehlendes SoFIFA blockiert den Import nicht.
* Alle Quellenwerte werden getrennt gespeichert.
* Der Importer führt keine interne Spielstärkeberechnung durch.
* Fortschritt ist im Creator-Mode sichtbar.
* Bestehende Spieler werden angezeigt.
* Änderungen zwischen Alt und Neu werden angezeigt.
* Neue Spieler können ausgewählt werden.
* Vorhandene Spieler können gezielt überschrieben werden.
* Alte importierte Werte bleiben beim Überschreiben nicht unbemerkt erhalten.
* Daten werden ohne CSV direkt in die Datenbank übernommen.
* Bestehende Beziehungen und Matchhistorien werden nicht zerstört.
* Importvorgänge werden protokolliert.
* Sicherheits- und API-Tests sind grün.
* Alle bestehenden Projekttests bleiben grün.
* Eine verständliche Installations- und Bedienungsanleitung ist vorhanden.

Keine Aufgabe als abgeschlossen markieren, solange nur die Oberfläche existiert, aber lokaler Importer, API, Kontrollansicht oder verbindlicher Datenbankimport noch fehlen.
